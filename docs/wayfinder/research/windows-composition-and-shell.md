# Windows composition and shell capability matrix

Research for [Wayfinder issue #2](https://github.com/themixednuts/komorebi/issues/2), performed on 2026-08-27. The target is a Windows 11-first personal Windows manager. Compatibility is useful only while it does not obstruct a cleaner design; personal continuity matters.

## Decision

Use documented Win32 shell and DWM contracts for the behavior Windows owns, and a manager-owned composition window for visuals Windows does not expose. In particular:

- Build workspace transitions and overview inside our own top-level overlay using DWM thumbnails or manager-rendered snapshots. Move, show, or hide the real windows only at a transition boundary. Do not promise direct transforms of another application's DWM surface.
- Implement scratchpads with ordinary top-level window state, positioning, and z-order. Invoke focus only from a user-triggered command, and treat elevated or capture-protected windows as explicit exceptions.
- Keep the AppBar implementation. It is the documented reservation contract and is already reserving the correct work area on this machine.
- Use layered-window opacity for third-party windows, with restoration of the original extended style. Treat foreign-window rounded-corner preferences and region clipping as experimental compatibility features, not foundations.
- Do not couple the workspace model to undocumented virtual-desktop COM interfaces. The public interface is adequate for membership queries, but not for enumerating, creating, switching, or animating Windows virtual desktops.
- Render custom shadows, glows, blur, and animation only on windows we own. Where an effect must visually follow another application, use a separate tracked overlay and accept that it can never become part of that application's compositor subtree.

This is still **native integration**: AppBar, DWM thumbnails, Win32 window positioning, DWM attributes, and DirectComposition are Windows contracts. The key distinction is ownership. DirectComposition explicitly requires the target `HWND` to belong to the caller; a foreign target returns `DCOMPOSITION_ERROR_ACCESS_DENIED` ([`CreateTargetForHwnd`](https://learn.microsoft.com/en-us/windows/win32/api/dcomp/nf-dcomp-idcompositiondesktopdevice-createtargetforhwnd)).

## Composition ownership boundary

DirectComposition is powerful inside our process: scalar visual properties can be animated independently of the UI thread, commits are atomic batches, and DWM samples them on its composition loop ([architecture](https://learn.microsoft.com/en-us/windows/win32/directcomp/architecture-and-components), [transforms](https://learn.microsoft.com/en-us/windows/win32/directcomp/transforms)). That does not grant access to the visual tree DWM maintains for another process. Consequently:

1. Moving a foreign `HWND` changes real window geometry and asks that application to participate.
2. Animating a thumbnail or captured image changes a visual we own and can be compositor-smooth.
3. There is no documented bridge that turns an arbitrary foreign top-level window into a transformable DirectComposition visual while leaving it interactive in place.

The correct workspace transition is therefore perceptual but honest: display an input-owning transition surface, animate live representations, atomically apply the manager workspace behind it, then remove the surface. Cancellation must restore the old workspace; destruction of a source must remove its visual without aborting the transition.

## Measured Windows 11 results

The disposable probes made no persistent system changes. The target was Windows build **26200.9168**, display version **25H2**, at **5120×1440 / 239 Hz** on an RTX 3090. The legacy `ProductName` registry string still reports “Windows 10 Home,” so the build number is the authoritative identifier here.

|---|---|---|
| `DwmIsCompositionEnabled` | `S_OK`, enabled | DWM composition active. |
| Foreign `DWMWA_WINDOW_CORNER_PREFERENCE` | set `S_OK`; readback `2` | Same-integrity cross-process corner preference is accepted on this build, but “if appropriate” remains discretionary. |
| Foreign layered alpha | set/readback succeeded at 173 | Opacity route is operational. Original style and alpha were restored. |
| Foreign topmost | set succeeded; `WS_EX_TOPMOST` observed; restore succeeded | Scratchpad/overlay z-order mechanics are operational. |
| 10,000 foreign `SetWindowPos` no-op calls | 964.760 ms total; 96.476 µs/call | API dispatch is cheap enough; this does not measure application repaint or visible animation quality. |
| 60 `DwmFlush` calls | p50 4.141 ms; p95 4.541 ms; range 3.250–5.086 ms | Consistent with the 239 Hz presentation interval. `DwmFlush` blocks for the caller's queued changes, not the whole session ([contract](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/nf-dwmapi-dwmflush)). |
| Foreign DWM thumbnail | registration/query `S_OK`; source 5120×50 | Overview primitive works across processes with a caller-owned destination. |
| Public virtual-desktop query | current/ID queries `S_OK` | Passive membership works. Foreign move-to-same-desktop returned `0x80070005` (`E_ACCESSDENIED`). |

Do not turn these measurements into universal budgets. They are single-machine baselines. In particular, the `SetWindowPos` loop used a minimized stock window and includes PowerShell/P/Invoke overhead while excluding real repaint work.

## Restrictions that must be first-class

- **Integrity and session:** a normal manager cannot mutate window data owned by a higher-UIPI process; `HWND` operations do not cross interactive sessions. Elevated applications need an explicit degraded mode, not silent retries.
- **Foreground ownership:** focus is not equivalent to z-order. Only user-driven commands should attempt foreground activation, and failure must preserve a useful visible state.
- **Capture policy:** protected or excluded windows may not appear in thumbnails/capture. Render a labeled placeholder; never bypass display affinity.
- **System policy:** transparency, Acrylic, and animation behavior can change under high contrast, reduced-motion expectations, Battery Saver, RDP/VM sessions, GPU fallback, HDR, or driver reset. The core manager must remain usable with every effect disabled.
- **Window churn:** applications recreate top-level HWNDs, change styles, add owned dialogs, constrain sizes, and hang. Every visual relationship must be disposable and keyed to a currently valid HWND.
- **Display churn:** monitor hotplug, rotation, scale, refresh, and Explorer restart invalidate rectangles and shell reservations. AppBar and overlays must renegotiate from monitor identity rather than cached pixels.
- **Full-screen and secure surfaces:** full-screen applications require AppBar z-order cooperation. Secure desktop/UAC and protected video are outside the manager's composition authority.

## Minimal follow-up feasibility spikes

These are the only composition uncertainties that should block specifications:

### C1: Live overview and workspace-transition surface

Build one disposable per-monitor topmost overlay containing DWM thumbnails for 20 representative windows. Exercise normal, minimized, cloaked, UWP-hosted, elevated, destroyed-mid-animation, excluded-from-capture, mixed-DPI, and full-screen cases. Measure command-to-first-frame, frame pacing, p95 completion time, memory, cancellation, focus restoration, and whether a transition can swap real workspace state without a visible flash. Success means no desktop flash, p95 first frame within two refresh intervals, correct placeholders, and exact restoration after cancellation.

### C2: Real-window motion versus visual-overlay motion

Animate the same representative windows using (a) `SetWindowPos` at the display cadence, (b) batched `DeferWindowPos`, and (c) a thumbnail overlay followed by one final real move. Record WinEvent count, target-thread stalls, repaint artifacts, frame pacing, CPU/GPU, and final geometry. This decides whether direct motion remains for intra-workspace rearrangement only.

### C3: Tracked Acrylic/blur overlay

Only if third-party-following blur is still desired, place a non-activating manager-owned Acrylic window behind a target and test occlusion, z-order, resize, full-screen, capture protection, RDP fallback, and 239 Hz tracking. Reject the feature if it cannot remain within one refresh interval or if it requires undocumented `SetWindowCompositionAttribute` behavior.

### C4: Foreign corner and region compatibility

Apply DWM corner preferences and then a reversible rounded `SetWindowRgn` to a matrix of Win32, Chromium, WinUI, Java, games, custom-frame, elevated, maximized, and borderless windows. Verify client pixels, hit testing, resize, shadow, screenshots, maximize/restore, HWND recreation, and complete restoration. Default to DWM preference; ship region clipping only behind per-application opt-in if it survives.

### C5: Passive Windows virtual-desktop settling

Observe user-driven `Ctrl+Win+Left/Right` switches. Poll public membership for known windows and measure the time until results stabilize, including pinned windows and Explorer restart. The result may support filtering manager events by current Windows desktop. It must not be used to switch or enumerate desktops through undocumented COM.

Everything else in this matrix is ready to become a behavior/specification ticket now: scratchpads, overview interaction semantics, AppBar lifecycle, opacity restoration, overlay z-order policy, capture placeholders, and the workspace-transition state machine around C1.
