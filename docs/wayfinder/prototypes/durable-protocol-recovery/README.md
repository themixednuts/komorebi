# Durable protocol recovery and latency prototype

This disposable native Rust executable answers [Prototype durable protocol recovery and latency](https://github.com/themixednuts/komorebi/issues/41). It uses a real overlapped Windows named pipe, strict numeric-key CBOR, process-death injection, a Drizzle-managed SQLite ledger, and bounded subscription lanes.

The prototype never touches the installed manager, its configuration, windows, themes, or AppBar. All durable state lives in a temporary directory.

## Selected design

- A file-backed SQLite database in WAL mode with `synchronous=FULL` is the canonical invocation ledger.
- Drizzle 0.1.16 generates the migration in `build.rs` and builds every application query. Application code contains no raw SQL.
- Identity, principal, digest, durable phase, manager revision, effect kind, result, event position, and compaction floor are ordinary typed columns.
- Action parameters are one versioned document stored through `#[column(blob)]`. `InvocationDocument` implements `DrizzleSQLiteColumn`; its fallible constructor creates canonical JSON bytes before admission and its decoder rejects non-BLOB or invalid JSON.
- `SelectInvocationLedgerRow`, generated by Drizzle, owns custom-column row decoding. `#[derive(SQLiteFromRow)]` handles plain projections such as the WAL pragma result. In Drizzle 0.1.16, a standalone derived row containing a custom column delegates to `rusqlite::FromSql`; it does not dispatch through `DrizzleSQLiteColumn`.
- The manager state owner registers a bounded mailbox and captures one immutable `Arc<ManagerSnapshot>` plus cursor in one operation.
- Publication uses `try_send`. Sixteen stalled first-party readers and sixteen stalled extension readers cannot block the state owner.
- First-party data lanes admit at most 1,024 frames or 4 MiB. Extension lanes admit at most 1 MiB. Each subscription has a separate 64-frame control lane.
- The replay ring retains at most 16 MiB and 60 seconds. A stale cursor or changed manager epoch returns `ResyncRequired`.
- A sequence-validated acknowledgement returns only data-lane credit. It does not report action success and cannot acknowledge an undelivered or already-acknowledged sequence.

The boundary review also applies the failure classes in [Bugs Rust Won't Catch](https://corrode.dev/blog/bugs-rust-wont-catch/). Process arguments remain `OsString`/`Path`, pipe names cross Win32 as native UTF-16, arithmetic at allocation and Win32-width boundaries is checked, fallible results are settled explicitly, and parser property tests cover hostile input. A production store directory must additionally be created with the manager's explicit ACL and opened from a trusted, manager-owned root; this disposable harness uses an isolated temporary directory.

JSON is used for the static measurement report only. It is not runtime state or a replay log.

## Run

From `harness`:

```powershell
cargo test --all-targets
cargo clippy --all-targets -- -D warnings
cargo run --release -- run ..\measurements\latest.json
```

The release run creates fresh named pipes and a fresh database. It launches a new client process for each cold-handshake sample and a new process for each injected crash boundary.

## Limits

The cold-handshake measurement includes process creation but not a reboot or a deliberately cold executable cache.

The extension-host containment prototype already proved the explicit current-user/AppContainer DACL. This executable reuses the contract boundary and authenticates each test client by the process ID reported by the connected pipe. It does not duplicate the LPAC launch and token proof.

This is evidence for a production design. It is not a compatibility layer and does not use the current manager's `SocketMessage`, `State`, or `Notification` types.
